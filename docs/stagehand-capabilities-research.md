# Stagehand capability audit

Reviewed 2026-09-25 using the Stagehand documentation MCP and installed SDK source. Scope: the current working tree, including existing uncommitted changes. Installed Stagehand is 3.7.0; package.json permits ^3.7.0. This is a static audit, with no preview execution or browser regression tests.

Greenlight already offloads natural-language actions, DOM condition checks, verdict extraction, action caching, and selector recovery to Stagehand. The clearest remaining simplification is consolidating browser control onto Stagehand's native page. Several other capabilities are useful, but would change Greenlight's behavior or require backend-specific handling.

| Priority | Opportunity | Assessment |
| --- | --- | --- |
| High | Remove the second Playwright CDP connection in src/execute.ts | Stagehand 3.7 already supplies every browser operation used by the production executor: pages/newPage, goto, console events, viewport, init scripts, evaluate, screenshot, and load-state waits. Use stagehand.context.pages()[0] and Stagehand's Page type. setViewportSize takes width and height separately; waitForLoadState takes a numeric timeout. Keep Playwright if other tests still require it. This removes duplicate browser ownership and close handling. [Page API](https://docs.stagehand.dev/v3/references/page), [context API](https://docs.stagehand.dev/v3/references/context). |
| Medium | Use screenshot extraction for the API-backed visual judge | Native extract supports screenshot input with a schema, potentially replacing screenshot capture plus generateText in judgeFromScreenshot. Installed extractHandler rejects screenshot when llmClient.type is not aisdk. The subscription adapter uses subscription-cli, so its custom screenshot path remains necessary. Preserve the separate visual model, uncertainty policy, and trusted-model rules. [Extract API](https://docs.stagehand.dev/v3/references/extract). |
| Medium | Add native metrics and selected history to diagnostics | Native metrics provide inference time and token counts by primitive; history records parameters, results, and timestamps. They can supplement current evidence. They cannot replace Greenlight's schema names, explicit throw records, durations, step/scope labels, or sanitization. SubscriptionLLMClient currently reports EMPTY_USAGE, so zero native token counts there mean unavailable accounting, not zero consumption. [History](https://docs.stagehand.dev/v3/best-practices/history), [observability](https://docs.stagehand.dev/v3/configuration/observability). |
| Medium | Parameterize dynamic act inputs | Native variables can reuse cached actions across changed input values when the instruction and page URL remain stable. The current plan/setup interfaces mostly pass raw instruction strings. Introduce explicit variables where useful rather than interpolating values into prompts. Installed ActCache keys retain the normalized full URL, so changing preview hosts still creates misses. [v3 caching](https://docs.stagehand.dev/v3/best-practices/caching). |
| Conditional | Scope extraction to known page regions | selector and ignoreSelectors reduce unrelated DOM context and model work. Expose optional scope only where the plan knows the relevant region; narrowing the final verdict too far can hide contradictory evidence. [Extract API](https://docs.stagehand.dev/v3/references/extract). |
| Conditional | Use agent for exploratory setup | v3 agent can handle multi-step tasks, bounded maxSteps, and, in experimental non-CUA mode, callbacks, abort signals, and structured output. It could replace an adaptive setup planner, but today's setup is an explicit ordered recipe with fresh wait_for/verify/ready checks. Agent completion is not a substitute for those assertions. Prototype only for genuinely adaptive preparation, retaining a separate final condition check and verifying subscription-client compatibility. [Agent API](https://docs.stagehand.dev/v3/references/agent). |

The native-page migration needs a focused browser regression with rrweb, console capture, navigation, screenshot fallback, and a page that never fires load. Installed Page.evaluate directly calls Runtime.evaluate after locating the execution context; it does not explicitly wait for load. Historical comments about driver settling are therefore not proof that today's native API is unsuitable. Retain the recording drain watchdog until measured behavior establishes that it is unnecessary.

Use native waitForSelector for conditions that explicitly identify an element and its visible/hidden state. Keep extract for semantic conditions such as whether the correct workspace is selected. Native history is appended after completed primitive calls in the installed implementation, so a thrown call can be absent; the current failure trace remains valuable.

Keep these responsibilities in Greenlight:

- Setup sequencing and semantic verification. Stagehand already performs the inspection and actions. Replacing the loop with agent would trade explicit assertions for autonomous choices. The current unbounded polling deserves a separate bounded-wait design; Stagehand's load-state wait does not verify arbitrary business conditions.
- Local rrweb recording and offline replay packaging. Native addInitScript and evaluate can host the recorder, but history is an operation log, not a DOM replay. The inspected public 3.7 page/context types expose no exposeBinding replacement. Browserbase recordings would change the local-browser architecture.
- Dialog policy. The inspected native types do not expose public dialog events or acceptance methods. The v3 docs demonstrate the same alert/confirm/prompt overrides currently used in Greenlight. Context-level addInitScript can centralize injection across future pages, but it does not make dialog assertions possible. [Context init scripts](https://docs.stagehand.dev/v3/references/context#addinitscript).
- Test-plan generation, PR context, execution versus assertion failure classification, result reporting, secret sanitization, and the subscription adapter. These are product-specific responsibilities, not duplicated browser automation.

Do not treat the default v4 documentation as an upgrade prescription. v4 removes agent and local cacheDir; its documented result caching requires Browserbase. Those changes directly affect Greenlight's local browser and subscription design. Evaluate any major-version migration separately. [v4 migration](https://docs.stagehand.dev/v4/migrations/v3).
